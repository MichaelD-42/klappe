# Building a deck from a storyboard

Use this when one person or one agent team builds a whole deck, many scenes at once. Each step ends before the next one starts.

1. Write one storyboard block per scene before any code. Use these keys, in order: `id`, `story point` (the one thing the room takes away), `motion idea` (what the motion teaches, or why a still frame is better), `character` (if the deck has one), `fx` (klappe names only; write `needs new helper (<name>)` for a gap), `transition`, `reuse`, `new assets`. Under it, write the `scene.md` text. The builder copies that text word for word.
2. Collect the gaps before you build. Every `needs new helper` becomes klappe work, and it is done first.
3. Build the shared parts once (frames, repeated scenes, deck helpers outside `sections/`). Prove them on two or three pilot scenes. Start the fan-out only after the deck owner approves the look.
4. Before the fan-out, ask the deck owner how to build, and wait for the answer: **inline**, you build the sections yourself, one after another in this session, with a checkpoint after each for the owner to look at; or **subagents**, one `klappe-builder` per section, in parallel, each with a fresh context, then the reviews below. Recommend subagents for many sections that share little, inline for a few sections or when the owner wants to steer each one. Without a subagent tool, build inline and say so.
5. Build each section; with subagents, one builder per section. Each builder owns its section folders. Start one `npm run dev` for the deck and give its URL to every builder for `shot --url`. A builder never edits shared parts: it lists the changes it wants in its hand-back. Each builder's brief carries acceptance criteria with ids (`AK-1`, ...); in a fix round, they are the deck owner's review entries for the scene, quoted. It runs `npm test -- --only <section> --strict`, so a look warning in its section fails, shoots its sections with `npm run shot -- <section> --last --sheet` and reads the PNGs, and commits by path. The orchestrator runs the full `npm test` once per wave, never two at once.
6. Review with three read-only reviewers in parallel: content (the brief's criteria, whether each scene makes a point for the room, facts, sources), look (overlap, safe area, contrast) and tech (the timeline rule, handles, steps). Tell them the task kind, `deck`. Give them one output format: a first line `VERDICT: PASS` or `VERDICT: FAIL`, then the content reviewer's `RUBRIC` lines (see `klappe/.rubrics/`), then one line per finding as `file:line — severity — problem — expected`, and nothing else (the gate reads every line with ` — ` as a finding). Pass them a list of known and accepted points, so nothing is reported twice.
7. Save each review to a file and run the gate: `node klappe/bin/verdict.mjs --kind deck --task <id> --log review-log.jsonl <reviews...>`. It rejects a review in the wrong format, and its `DECISION` line says where the work goes: `merge`, `builder` (one fix round on one merged fix list), `planner` (the brief was misread; start again from the brief) or `owner` (the deck owner decides, for example whether to cut a scene that makes no point). It exits 0 for `merge`, 1 for the others and 2 for a review in the wrong format. In the klappe repo itself the command is `node bin/verdict.mjs`. Then the deck owner walks the deck. After about 30 tasks, read `review-log.jsonl`: a dimension that always gives the same level is not judging anything; a scene or criterion that keeps coming back wants a check in `klappe test`.
8. When a text changes, change it in `scene.md` and in the storyboard. A `scene.ts` that reads `ctx.doc` follows by itself.
