# Building a deck from a storyboard

Use this when one person or one agent team builds a whole deck, many scenes at once. Each step ends before the next one starts.

1. Write one storyboard block per scene before any code. Use these keys, in order: `id`, `story point` (the one thing the room takes away), `motion idea` (what the motion teaches, or why a still frame is better), `character` (if the deck has one), `fx` (klappe names only; write `needs new helper (<name>)` for a gap), `transition`, `reuse`, `new assets`. Under it, write the `scene.md` text. The builder copies that text word for word.
2. Collect the gaps before you build. Every `needs new helper` becomes klappe work, and it is done first.
3. Build the shared parts once (frames, repeated scenes, deck helpers outside `sections/`). Prove them on two or three pilot scenes. Start the fan-out only after the deck owner approves the look.
4. Before the fan-out, ask the deck owner how to build, and wait for the answer: **inline**, you build the sections yourself, one after another in this session, with a checkpoint after each for the owner to look at; or **subagents**, one `klappe-builder` per section, in parallel, each with a fresh context, then the reviews below. Recommend subagents for many sections that share little, inline for a few sections or when the owner wants to steer each one. Without a subagent tool, build inline and say so.
5. Build each section; with subagents, one builder per section. Each builder owns its section folders. Start one `npm run dev` for the deck and give its URL to every builder for `shot --url`. A builder never edits shared parts: it lists the changes it wants in its hand-back. It runs `npm test -- --only <section>`, shoots its sections with `npm run shot -- <section> --last --sheet` and reads the PNGs, and commits by path. The orchestrator runs the full `npm test` once per wave, never two at once.
6. Review with three read-only reviewers in parallel: content (text matches `scene.md`, facts, sources), look (design rules, overlap, safe area, contrast) and tech (the timeline rule, handles, steps). Give them one output format: a first line `VERDICT: PASS` or `VERDICT: FAIL`, then one line per finding as `file:line — severity — problem — expected`, and at most five top fixes. Pass them a list of known and accepted points, so nothing is reported twice.
7. Merge all findings into one fix list per round, in one file. Run one fix round on it. Then the deck owner walks the deck.
8. When a text changes, change it in `scene.md` and in the storyboard. A `scene.ts` that reads `ctx.doc` follows by itself.
